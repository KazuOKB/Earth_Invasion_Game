# アーキテクチャ設計書

## 1. この文書の目的

この文書は、新しいPythonコードの分け方をまとめます。

目標は次の3つです。

- 読みやすくする
- テストしやすくする
- 後から変更しやすくする

難しい仕組みは必要になるまで追加しません。

## 2. 基本方針

ゲームのルールとPygameの処理を分けます。

```text
Pygameの入力
    ↓
ゲーム用の命令
    ↓
ゲーム状態を更新
    ↓
描画と音声
```

ゲームのルール側では`pygame`をimportしません。

## 4. 依存関係

依存関係は一方向にします。

```text
pygame_app → gameplay → Python標準ライブラリ
```

`gameplay`から`pygame_app`は参照しません。

HUDの高さは`pygame_app/hud.py`で管理します。
Pygame側からゲームルールへゲーム領域の上端を渡します。
これにより、ゲームルール側もHUDへ物体を入れません。

## 5. gameplayの役割

`gameplay`はゲームのルールを持ちます。

- プレイヤー
- 敵
- 弾
- 移動
- 当たり判定
- ダメージ
- 侵略ゲージ
- ステージ進行
- ボスの出現判定
- クリア判定
- ゲームオーバー判定

Pygameの画像や音声は扱いません。

## 6. pygame_appの役割

`pygame_app`はPygame固有の処理を持ちます。

- ウィンドウを作る
- キーボード入力を受け取る
- 画像を描く
- 宇宙背景とHUDを描く
- 文字を描く
- 音を鳴らす
- 画面を切り替える

`navigation.py`は、現在の画面とキーから次の操作を決めます。
この処理はPygameのイベントから分けています。
そのため、画面を開かずに画面遷移をテストできます。

`screens.py`は、タイトル、ルール、結果画面を描画します。
ゲーム画面の描画とは分けます。

アプリケーションの画面は次の5種類です。

- タイトル
- ルール
- ゲーム
- ゲームオーバー
- ゲームクリア

タイトル、ルール、結果画面では、ゲーム状態を更新しません。
ゲームを開始または再挑戦するときは、ゲーム状態を初期化します。
画面を切り替えると、固定更新用に残っていた時間も破棄します。

## 7. ゲーム状態の管理

ゲーム全体は`GameSession`が管理します。

`GameSession`は次の状態を持ちます。

- プレイヤー
- 敵の一覧
- プレイヤーの弾
- 敵の弾
- 現在の区間
- 侵略ゲージ
- スコア

敵は並列の配列で管理しません。
敵ごとに1つのオブジェクトを作ります。

ゲームルールへ渡す値は`settings.py`の小さな設定クラスへまとめます。

- `PlayerSettings`: プレイヤーの大きさ、速度、体力、無敵時間
- `WeaponSettings`: ビームの速度と発射間隔
- `MeteorSettings`: 隕石の大きさ、出現間隔、速度
- `ChaserSettings`: 追尾敵の大きさ、出現間隔、速度
- `ShooterSettings`: 攻撃敵の大きさ、出現間隔、移動、射撃
- `BossSettings`: ボスの大きさ、耐久力、移動、射撃
- `InvasionSettings`: ゲージ上限と敵ごとの増加量

これにより、`GameSession.create()`へ長い引数を並べずに済みます。
JSONを読む処理とゲームルールも分離できます。

## 8. 状態の名前

数字のフラグは使いません。
状態には名前を付けます。

```python
class GamePhase(Enum):
    METEOR = auto()
    CHASER = auto()
    SHOOTER = auto()
    BOSS = auto()
```

ゲーム全体の状態は別の名前で管理します。

```python
class GameStatus(Enum):
    PLAYING = auto()
    GAME_OVER = auto()
    GAME_CLEAR = auto()
```

`GamePhase`の名前はJSONの`id`と対応させます。
`GameStatus`はプレイ中か終了しているかを表します。

現在の区間と経過時間は`StageProgress`が管理します。
区間ごとの時間は`StageSchedule`へ渡します。
この2つはPygameやJSONを直接扱いません。

## 9. 時間の扱い

ゲーム内の時間は秒で扱います。

速度は「1秒で何ピクセル動くか」で表します。
Pygameのタイマーイベントでステージを進めません。

ゲームの更新は固定間隔で行います。
初期値は1秒に60回です。

```text
固定更新間隔 = 1 / 60秒
```

1フレームが長くなっても、一度に大きく動かさないようにします。

Pygameから受け取った経過時間は、固定更新の回数へ変換します。
余った時間は次のフレームへ持ち越します。

隕石、追尾する敵、攻撃する敵の区間は設定時間で進みます。
終盤の時間が過ぎても、侵略ゲージが満タンでなければ終盤に留まります。
時間とゲージの両方を満たすとボス区間へ進みます。
ボス区間には時間制限を設けません。

ウィンドウの移動などで長時間止まった場合は、最大0.25秒分だけ更新します。
これにより、一度に大量の更新が実行されることを防ぎます。

## 10. ステージ設定

ステージ時間は`src/earth_invasion/data/`のJSONから読み込みます。

設定をPythonパッケージ内に置くことで、インストール後も読み込めます。
起動時に`--data-directory`を指定すると、別の設定へ差し替えられます。

通常用とテスト用は同じ形式にします。

```json
{
  "profile": "normal",
  "invasion_target": 100,
  "phases": [
    {
      "id": "meteor",
      "duration_seconds": 30.0
    }
  ]
}
```

読み込み時に次を確認します。

- `profile`が空ではない
- `invasion_target`が0より大きい
- 必要な区間がすべてある
- 区間の順番が正しい
- 時間が0より大きい
- ボスの時間だけが`null`になっている

テスト設定で新しい画面を起動するコマンドは次のとおりです。

```bash
uv run earth-invasion --stage-profile test
```

画面を開かずに設定だけを確認する場合は、次のように実行します。

```bash
uv run earth-invasion --stage-profile test --check-config
```

プレイヤーと攻撃の共通設定は`gameplay.json`から読み込みます。
このファイルには次の値を置きます。

- 内部解像度
- 1秒あたりの更新回数
- プレイヤーの最大体力
- 被弾後の無敵時間
- プレイヤーの移動速度
- ビームの発射間隔
- ビームの移動速度
- 隕石の出現間隔
- 隕石の最低速度と最高速度
- 追尾敵の出現間隔
- 追尾敵の横移動速度と上下追尾速度
- 攻撃敵の出現間隔と横移動速度
- 攻撃敵の射撃間隔と敵弾の速度
- ボスの最大体力、上下移動速度、射撃間隔、敵弾速度
- 敵を倒したときの侵略ゲージ増加量

## 11. 画面の拡大

750×500の内部画面を1つ作ります。
ゲームは内部画面へ描画します。

上部100ピクセルをHUDにします。
ゲーム領域は`y=100`から`y=500`までです。
プレイヤーと敵の移動、生成位置、敵弾の削除判定に同じ境界を使います。
最後にHUDを描画するため、ゲーム内物体は文字やゲージを隠しません。

最後に内部画面をウィンドウへ拡大します。
縦横比は維持します。

```text
倍率 = min(ウィンドウ幅 / 750, ウィンドウ高さ / 500)
```

拡大した画面は中央に置きます。
余った部分は黒で表示します。


## 12. 入力

Pygameのキーを、そのままゲームへ渡しません。

入力を次のような命令へ変換します。

```python
@dataclass(frozen=True, slots=True)
class PlayerCommand:
    vertical_direction: int
    fire_pressed: bool
```

`vertical_direction`は次の値を使います。

- `-1`: 上
- `0`: 移動なし
- `1`: 下

`fire_pressed`は`Z`を押している間、`True`になります。
ゲームルール側は発射間隔を確認してからビームを作ります。

## 13. ゲームイベント

ゲーム内で起きたことをイベントとして返します。

例は次のとおりです。

- 敵を倒した
- プレイヤーがダメージを受けた
- 区間が変わった
- ボスが登場した
- ゲームをクリアした

Pygame側はイベントを見て、音や演出を再生します。

最初から大きなイベントシステムは作りません。
更新結果としてイベントの一覧を返します。

## 14. 当たり判定

最初は四角形の当たり判定を使います。

プレイヤー、敵、弾は当たり判定用の大きさを持ちます。
画像の大きさと当たり判定の大きさは分けられます。

ビームと隕石が重なった場合は、両方を削除します。
1本のビームが同時に破壊できる隕石は1個です。
隕石を破壊すると、設定された値だけ侵略ゲージを増やします。
ビームと追尾敵が重なった場合も、両方を削除します。
追尾敵を破壊すると、設定された値だけ侵略ゲージを増やします。
ビームと攻撃敵が重なった場合も、両方を削除します。
攻撃敵を破壊すると、設定された値だけ侵略ゲージを増やします。
侵略ゲージはステージ設定の最大値を超えません。

ボス区間へ入ると、残っている通常敵と敵弾を削除します。
ボスはビームが当たるたびに体力を1減らします。
ボスの体力が0になるとゲームクリアへ移行します。

プレイヤーが隕石、追尾敵、攻撃敵、敵弾に触れると、体力を1減らします。
接触した敵または敵弾は削除します。
同じ更新で複数の敵に触れても、減る体力は1です。
被弾後は設定された時間だけ無敵になります。
無敵中に敵へ触れた場合は、敵だけを削除します。

必要になった場合だけ、画像の形に合わせた判定を検討します。

## 15. 乱数

乱数は`GameSession`の外から渡します。

```python
random_source = random.Random(seed)
```

テストでは同じ`seed`を使います。
同じ条件で同じ敵を出せます。

## 16. テスト方針

画面を開かないテストを中心にします。

最初に次をテストします。

- 固定時間から必要な更新回数を計算できる
- 長時間停止後の更新回数が制限される
- プレイヤーが設定した速度で上下に移動する
- プレイヤーが画面の上下端で止まる
- ビームが設定した発射間隔を守る
- ビームが設定した速度で移動する
- 画面外へ出たビームが削除される
- 隕石が設定した間隔で出現する
- 隕石の位置と速度を同じ乱数seedで再現できる
- 隕石が固有の速度で左へ移動する
- 画面外へ出た隕石が削除される
- ビームと隕石が重なると両方が削除される
- 1本のビームが破壊する隕石は1個だけになる
- 隕石を破壊すると侵略ゲージが設定値だけ増える
- 侵略ゲージが最大値を超えない
- 追尾敵が追尾敵の区間だけで出現する
- 追尾敵が左へ進みながらプレイヤーを上下に追う
- 追尾敵が同じ乱数seedで同じ位置に出現する
- 画面外へ出た追尾敵が削除される
- 追尾敵を破壊すると侵略ゲージが設定値だけ増える
- 攻撃敵が終盤だけで出現する
- 攻撃敵が左へ移動する
- 攻撃敵が設定間隔でプレイヤーへ向けて弾を撃つ
- 敵弾が設定速度で移動し、画面外で削除される
- 攻撃敵を破壊すると侵略ゲージが設定値だけ増える
- 侵略ゲージと時間の条件を満たすとボスが出現する
- ボスが上下端で向きを変える
- ボスが設定間隔でプレイヤーへ向けて弾を撃つ
- ビームが当たるとボスの体力が1減る
- ボスの体力が0になるとゲームクリアになる
- ゲームクリア後は位置、時間、弾が更新されない
- ゲームクリア後の再挑戦でボスと状態が初期化される
- 隕石、追尾敵、攻撃敵、敵弾との接触で体力が1減る
- 同時に複数の敵へ触れても体力は1だけ減る
- 接触した敵が削除される
- 無敵時間中は追加のダメージを受けない
- 無敵時間の終了後は再びダメージを受ける
- 体力が0未満にならない
- 体力が0になるとゲームオーバーになる
- ゲームオーバー後は位置、時間、敵が更新されない
- 再挑戦で体力、敵、弾、ゲージ、区間が初期化される
- 再挑戦後にゲームを再び更新できる
- 時間で区間が進む
- テスト設定では短時間でボスまで進む
- 敵を倒すと侵略ゲージが増える
- 侵略ゲージが足りない場合はボスが出現しない
- 侵略ゲージが満タンになるとボスが出現する
- 終盤の設定時間より前にはボスが出現しない
- ビームは発射間隔より早く発射されない
- 攻撃が当たると体力が減る
- ボスを倒すとクリアになる
- 同じ乱数シードで同じ結果になる

Pygame側では最低限の起動テストを行います。

自動テストでは、実際に2秒待ちません。
更新処理へ経過時間を直接渡します。

## 17. 読みやすさのルール

- 1つの関数に多くの仕事をさせない
- 短く意味が分かる名前を使う
- 型ヒントを書く
- 数字へ名前を付ける
- コメントには理由を書く
- 同じ処理を複数の場所へ書かない
- 難しい抽象化は必要になるまで作らない

テストも使用例として読める形にします。

## 18. 採用しないもの

最初の実装では次を使いません。

- 本格的なECS
- DIコンテナ
- グローバルなイベントバス
- 深い継承
- 必要性のない抽象クラス

## 19. 既存コードからの移行

新しい実装が動くまで、現在のゲームは残します。

移行は次の順番で行います。

1. uv環境と新しい起動処理
2. 固定サイズの画面
3. プレイヤー移動
4. ビーム
5. 敵と当たり判定
6. ステージ進行
7. 侵略ゲージ
8. ボス
9. タイトルと結果画面
10. 旧コードの削除

各段階でテストを追加します。
